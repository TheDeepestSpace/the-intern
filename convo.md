## 2026-08-02: GitHub App "Secrets" permission vs fine-grained PAT for managing Actions secrets — answered
User asked (replying to an earlier missed message re: the-intern PR #43) whether to just grant the-intern-bot's GitHub App a write-secrets scope instead of the PAT-based approach an earlier session suggested there (a fine-grained PAT + `REPO_ADMIN_TOKEN` repo secret, reasoning that installation tokens can't manage Actions secrets).
- Verified via GitHub's official `permissions-required-for-github-apps` docs (not from memory): GitHub Apps DO have a repo-level **"Secrets"** permission; set to **Read & write** it grants `PUT`/`DELETE /repos/{owner}/{repo}/actions/secrets/{secret_name}`. (An older 2022 community discussion claiming no such permission exists is stale/superseded.)
- Checked `scripts/mint-installation-token.js`: it mints tokens via `POST .../access_tokens` with **no `permissions` body** — so it auto-inherits whatever the App is currently granted, no code change needed once the App permission is added.
- **Answer given**: yes, adding Secrets:write to the App works and avoids managing a second token. Trade-off flagged: a fine-grained PAT scopes to one repo only; the App permission applies everywhere the-intern-bot is installed (the-intern, svsch, etc.) — broader blast radius if a token ever leaked, though the bot already has broad contents/PR-write access there so likely an acceptable trade. Steps given: App settings → Permissions & events → Repository permissions → Secrets → Read and write → Save, then approve the updated permission on the installation(s).
- Purely advisory, nothing filed or changed.
- **Follow-up answered**: user asked whether "Read & write" on Secrets means the App can arbitrarily read a secret's value. No — GitHub's Actions secrets API has no plaintext-read endpoint at any permission level; GET only returns metadata (name/created_at/updated_at), writes must be pre-encrypted client-side (libsodium sealed box) against the repo's public key, and GitHub only ever stores ciphertext. Same restriction applies in the web UI (even repo admins can't view values, only overwrite/delete). So "Read" there governs listing names/metadata, not values — platform guarantee, not a permission-scoping nuance.
