## 2026-08-02: RFMem investigation — completed, findings reported, filing NOT yet done
Earlier follow-up thread (RFMem investigation dropped once already) was restarted: user re-sent the diagram photo + pointed at `UTOSS/risc-v` `boris/svsch` branch `src/modules/Instruction_Decode/registerFile.v` (a standard `reg [31:0] RFMem [0:31]` regfile: 2 async ternary reads, 1 sync write block = per-index write `RFMem[Addr3]<=dataIn` + full-array reset loop `for(i...) RFMem[i]<=0`). Cloned svsch to `/tmp/svsch` and read `src/parser/backend_cpp/src/extractor_parts/*.inc` (the C++ UHDM→JSON backend) to find root cause. Findings (reported to user via Telegram in full, condensed here):
1. **No memory node kind exists** — svsch only ever renders array writes as a stacked "REGISTER" (isArrayNode flag + CSS skin layers), never a distinct RAM/memory shape. Bigger design gap, own issue.
2. **Continuous-assign array reads never get array-tagged** — the black "COMBINATIONAL" boxes in the diagram are the ternary reads/write-mux, built by the generic expression-lowering path (`expressions.inc`/`modules.inc` `lowerAggregateAssignment`), which has zero awareness of `mod.arrayDimensions`/`isArrayNode` (only the procedural/always-block write path in `procedural.inc` tags arrays). So `RFMem[Addr1]`/`RFMem[Addr2]` reads render as opaque unlabeled boxes with no link back to RFMem.
3. **Confirmed code bug** (high confidence, direct cause of the two "conflicting" REGISTER boxes): `procedural.inc`'s array-merge logic (~line 477) is meant to collapse all writes to one array into a single stacked register + one address mux. It dedupes the register node (`array_reg_exists` check) but the `addr_mux` (`id = "mux:" + mod.name + reg_base + "_addr"`) is pushed unconditionally per distinct index expression, with no existence check. Here there are two index expressions into RFMem (`Addr3` from the write, `i` from the reset loop) → two mux nodes silently collide on one ID → merge fails, producing two disconnected/"conflicting" register-looking nodes instead of one memory block.
4. **Unconfirmed/open**: whether the merge logic even engages for this file's legacy `reg [31:0] RFMem [0:31] /* synthesis ramstyle = M10K*/;` declaration style vs `logic`-typed arrays (merge silently bails if `reg_base` isn't found in `mod.internalSignals`). Tried to get a live Surelog+UHDM run to confirm — the pip `uhdm` wheel only ships Python bindings, no C++ headers/cmake package needed to build svsch's backend from source (`find_package(UHDM REQUIRED)` in CMakeLists.txt has no source here); would need building UHDM/Surelog from source (large C++ project, likely 20-40+ min), not attempted given single-shot session constraints. Needs a real run before anyone touches code here.
