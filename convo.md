## 2026-07-29: Ternary operator support in svsch
- Researched and confirmed svsch has no support for the `?:` conditional operator — it falls through to a generic `comb` block in both the C++/UHDM backend (`getOrPromoteExpr` in `src/parser/backend_cpp/src/extractor_parts/expressions.inc` has no `isConditionalOperation` check, unlike ALU/inverter/replicate which each have one) and the text-fallback parser (`extractContinuousAssigns` in `src/parser/textExtractor.ts`).
- Filed issue: https://github.com/TheDeepestSpace/svsch/issues/72 — includes root-cause file/line refs, proposed design (hook ternary into `getOrPromoteExpr` the same way ALU/inverter are, so nesting and ternary-embedded-in-larger-expressions both fall out of the existing recursion for free — recommended over the user's initial "whole-expr-only" heuristic), syntax-book YAML test cases needed (`test/syntax-book/cases/muxes.yaml`), and visual regression fixtures needed (`test/visual/fixtures/`, pattern from `test/visual/mux.visual.spec.ts`).
- Not yet implemented. Next step if user wants it built: comment `@the-intern-bot <instructions>` on issue #72 to kick off the dispatcher pipeline, or the user may want to discuss the open questions in the issue first (port label convention `1`/`0` vs `true`/`false`; whether same-selector ternary chains should eventually collapse to one N-way mux like case statements do).
- User drew an analogy to a prior discussion about `a+b+c+d` addition chains: since ALU ops there are associative/commutative, there's genuine ambiguity in tree shape (balanced vs chained) that the tool can't resolve without knowing synthesis behavior — hence leaning toward a comb-block fallback for "anything more than simple" expressions. Asked whether the same reasoning should apply to ternary chains.
- I pushed back: `?:` has fixed right-associative precedence, so unlike `+`, the AST/parse tree already unambiguously encodes the nesting structure — rendering nested muxes isn't guessing at synthesis, it's faithfully transcribing what's already in the parse tree. **User agreed** ("allow unlimited nesting on this and cross that river of ugliness when we get there").
- Decision recorded as a comment on #72: https://github.com/TheDeepestSpace/svsch/issues/72#issuecomment-5113375843 — unlimited nested ternary-mux rendering via `getOrPromoteExpr` recursion, no depth-based comb-block fallback for now; revisit with a *visual complexity* threshold later if deep chains render poorly (same idea as case-statement collapsing), not baked in upfront.
- **Resolved 2026-07-29**: user chose bit-literal style port labels — `1'b1` / `1'b0` (not `true`/`false`). Decision posted as a comment on #72: https://github.com/TheDeepestSpace/svsch/issues/72#issuecomment-5113404515
- Both open design questions on #72 are now resolved (unlimited nesting via `getOrPromoteExpr` recursion + `1'b1`/`1'b0` port labels). Nothing else blocking implementation. Next step: user says go, then comment `@the-intern-bot <instructions>` on #72 to kick off the dispatcher pipeline and actually implement ternary support.
- **Kicked off 2026-07-29**: posted implementation instructions as a comment on #72 (https://github.com/TheDeepestSpace/svsch/issues/72#issuecomment-5113429789) to trigger svsch's own dispatcher pipeline — covers both backends, port labels, no depth fallback, syntax-book + visual regression tests, and opening a PR when done. ## 2026-07-29: Root cause found — why dispatcher never used svsch's own devcontainer image
User asked directly why the dispatcher fell back to the-intern-dev image instead of svsch's repo-specific one (correcting the wrong assumption from the #5 investigation above — svsch **does** publish a `-dev` image). Investigated `detect-image` job in `.github/workflows/dispatcher.yml` and confirmed two independent, compounding bugs:
1. **GHCR auth is wrong**: the check does `curl -f -H "Authorization: Bearer $GH_TOKEN" https://ghcr.io/v2/OWNER/REPO-dev/tags/list`, passing the raw GitHub App installation token straight through as a Bearer token. GHCR (Docker Registry v2) rejects this — verified directly, got `403 {"errors":[{"code":"DENIED","message":"invalid token"}]}`. The correct flow requires an extra token-exchange step: `GET https://ghcr.io/token?service=ghcr.io&scope=repository:OWNER/REPO:pull` (basic auth) to get a scoped registry bearer token, *then* use that for `/v2/.../tags/list`. Because the check always 403s, `curl -f` always "fails" and the workflow silently falls back to `the-intern-dev:latest` for every repo, regardless of whether a custom image exists.
2. **Tag-prefix mismatch**: even with auth fixed, the dispatcher assumes tag `:latest`. svsch's own `.github/workflows/docker-image.yml` + `ci.yml` build the dev image with `tag-prefix: dev-`, so on the default branch the published tag is `dev-latest`, not `latest` (confirmed via GHCR tag list: `dev-latest`, `dev-branch-master`, `dev-pr-10`...`dev-pr-71`, no bare `latest`). So `ghcr.io/thedeepestspace/svsch-dev:latest` would still fail to pull even after bug 1 is fixed.
- **Filed issue**: https://github.com/TheDeepestSpace/the-intern/issues/6 — full root cause writeup + suggested fixes (proper GHCR token exchange; check for `dev-latest` or otherwise reconcile the dispatcher's tag assumption with each repo's actual publish convention).
