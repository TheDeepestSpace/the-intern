## 2026-08-07: explained why usage-limit retries exhaust before a multi-day outage actually lifts
User asked why svsch#100/#102/#136 (see above) burned all 3 retries when Claude's limit was reportedly out ~3 days — i.e. there was seemingly never a valid point to retry. Read `detect-usage-limit.js`/`pending-retries-store.js`/`poll-pending-retries.js`/`handle-agent-outcome.js` to answer precisely (no code changed, pure Q&A).
**Root cause identified (not yet filed as an issue):** `retryAfter` is always parsed from the live CLI failure text (e.g. `"You've hit your session limit · resets 6:20pm (UTC)"`), which only ever reports the next short-term (5-hour session) reset — never the true duration of a longer plan/weekly/monthly-level stall. Each `upsertStall` call re-parses a fresh near-term time from whatever message the *latest* attempt produced (doesn't touch `retryCount`); only `markFired` (the poller, on actual re-fire) increments the counter, default cap 3. Net effect: on a multi-day outage the system retries roughly once a day, hits the wall again each time, and exhausts its fixed 3-retry budget in ~3 days — right around when a real reset might have happened, but with no way to know that from the text, so it's structurally guesswork, not a bug in the strict sense.
**Why this matters:** explains the "used up all 3/3, manual re-trigger needed" pattern from the entry above — expected behavior given current design, not a malfunction. No fix proposed yet (e.g. exponential backoff on repeated same-key stalls, or an escape hatch to detect "still the same session-limit text as last time" and back off further instead of re-parsing the same short window). Sent full walkthrough via Telegram; did not ask if user wants this filed as an issue — worth raising next time it comes up.
