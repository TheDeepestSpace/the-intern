## 2026-07-29: Ternary operator support in svsch
- Researched and confirmed svsch has no support for the `?:` conditional operator — it falls through to a generic `comb` block in both the C++/UHDM backend (`getOrPromoteExpr` in `src/parser/backend_cpp/src/extractor_parts/expressions.inc` has no `isConditionalOperation` check, unlike ALU/inverter/replicate which each have one) and the text-fallback parser (`extractContinuousAssigns` in `src/parser/textExtractor.ts`).
- Filed issue: https://github.com/TheDeepestSpace/svsch/issues/72 — includes root-cause file/line refs, proposed design (hook ternary into `getOrPromoteExpr` the same way ALU/inverter are, so nesting and ternary-embedded-in-larger-expressions both fall out of the existing recursion for free — recommended over the user's initial "whole-expr-only" heuristic), syntax-book YAML test cases needed (`test/syntax-book/cases/muxes.yaml`), and visual regression fixtures needed (`test/visual/fixtures/`, pattern from `test/visual/mux.visual.spec.ts`).
- Not yet implemented. Next step if user wants it built: comment `@the-intern-bot <instructions>` on issue #72 to kick off the dispatcher pipeline, or the user may want to discuss the open questions in the issue first (port label convention `1`/`0` vs `true`/`false`; whether same-selector ternary chains should eventually collapse to one N-way mux like case statements do).
- User drew an analogy to a prior discussion about `a+b+c+d` addition chains: since ALU ops there are associative/commutative, there's genuine ambiguity in tree shape (balanced vs chained) that the tool can't resolve without knowing synthesis behavior — hence leaning toward a comb-block fallback for "anything more than simple" expressions. Asked whether the same reasoning should apply to ternary chains.
- I pushed back: `?:` has fixed right-associative precedence, so unlike `+`, the AST/parse tree already unambiguously encodes the nesting structure — rendering nested muxes isn't guessing at synthesis, it's faithfully transcribing what's already in the parse tree. **User agreed** ("allow unlimited nesting on this and cross that river of ugliness when we get there").
- Decision recorded as a comment on #72: https://github.com/TheDeepestSpace/svsch/issues/72#issuecomment-5113375843 — unlimited nested ternary-mux rendering via `getOrPromoteExpr` recursion, no depth-based comb-block fallback for now; revisit with a *visual complexity* threshold later if deep chains render poorly (same idea as case-statement collapsing), not baked in upfront.
- Only remaining open question on #72: port label convention (`1`/`0` vs `true`/`false`). Not yet decided. Next step once settled: comment `@the-intern-bot <instructions>` on #72 to kick off implementation via the dispatcher pipeline.
- Gave user pros/cons for each labeling convention (not yet posted to the issue, not yet decided): `1`/`0` favored for RTL idiom (SV conditions are bit values, no real bool type), compactness under nesting, and likely consistency with how svsch already labels other muxes (case/if-else) if those use value labels rather than true/false — haven't actually confirmed that in the svsch source. `true`/`false` favored for at-a-glance readability and visually distinguishing ternary-derived muxes from value-selected ones, but reads as a software abstraction bolted onto a hardware diagram and costs more space when nested. Net lean: `1`/`0`, contingent on confirming existing mux label style in svsch.
